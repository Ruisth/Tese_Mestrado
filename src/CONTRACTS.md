Translated into British English on 2026-08-14 under the language policy; the normative content is unchanged from v1.1 (2026-08-08).

> Derived from archived plan v1.0 §5; under plan v1.1/v1.2 §1 this file is

## 1. MQTT

| Item | Value |
|---|---|
| Port | `8883` (TLS) |
| QoS | 1 |
| Authentication | username/password (Mosquitto `password_file`) + TLS server-auth |
| Telemetry topic | `c2dt/{egw_id}/{device_uuid}/telemetry` |
| Controller filter | `c2dt/+/+/telemetry` |
| Anonymous access | forbidden |
| Local dev/tests | `--no-tls` profile permitted only on `localhost` and never in benchmarks |

Dev users (generated by script, never committed): `egw-controller`,
`egw-simulator`. ACL: the simulator only publishes to `c2dt/#`; the controller
only subscribes.

## 2. Common event envelope (schema_version 1.0.0)

All telemetry payloads include (see `schemas/telemetry-envelope-v1.schema.json`):

| Field | Type/rule |
|---|---|
| `schema_version` | semver string, `1.0.0` |
| `run_id` | string `[A-Za-z0-9._-]{1,64}`, immutable per run |
| `message_id` | UUID v5 (namespace below) derived from `run_id`, `device_uuid`, `seq` |
| `seq` | integer ≥ 0, monotonically increasing per device |
| `ts` | RFC 3339 UTC with `Z` suffix, ms resolution |
| `egw_id` | string `[A-Za-z0-9._-]{1,64}` |
| `device_uuid` | stable UUID v4 of the device |
| `device_type` | `smartwatch` \| `smart_ring` \| `smart_clothing` |

**UUID v5 namespace:** `6b1a3f52-8c1e-5e2b-9f0d-c2d7a1e4b8a0` (project constant,
`egw_simulator.envelope.EGW_UUID_NAMESPACE`). Name: `"{run_id}:{device_uuid}:{seq}"`.
The controller repeats the same constant in `egw_controller.service.EGW_UUID_NAMESPACE`:
the simulator and the controller are separate deliverables and only the controller
goes into the deployment image, so the controller never imports the simulator at
runtime. The controller's tests assert the equality of the two constants,
preventing silent divergence.

## 3. Per-device measurements (top-level fields, alongside the envelope)

| device_type | Nominal rate | Fields | Ranges |
|---|---:|---|---|
| `smartwatch` | 1.0 msg/s | `heart_rate_bpm` int; `lat`, `lon` number | 25–250; −90..90; −180..180 |
| `smart_ring` | 0.2 msg/s | `skin_temp_c` number; `spo2_pct` int | 30.0–43.0; 50–100 |
| `smart_clothing` | 10.0 msg/s | `accel_x/y/z` number (m/s²); `breathing_rpm` number | −78..78; 4–60 |

Split of the aggregate `--rate`: fixed proportion `1 : 0.2 : 10` (plan §5.6).
E.g. `--rate 11.2` → smartwatch 1.0 + ring 0.2 + clothing 10.0.

Schemas: `schemas/smartwatch-v1.schema.json`, `schemas/smart-ring-v1.schema.json`,
`schemas/smart-clothing-v1.schema.json` (draft 2020-12, `unevaluatedProperties: false`).

## 4. Ditto twins

| Item | Value |
|---|---|
| `thingId` | `org.c2dta:{device_uuid}` |
| `policyId` | `org.c2dta:{device_uuid}` (dedicated policy per twin) |
| Attributes | `device_type`, `egw_id`, `schema_version` |
| Authorised subject | `pre:egw-controller` (Ditto gateway pre-authentication; READ+WRITE on `thing:/` and `policy:/`) |

Features per type:

| device_type | Features → properties |
|---|---|
| `smartwatch` | `vitals` → `heart_rate_bpm`; `location` → `lat`, `lon` |
| `smart_ring` | `thermo` → `skin_temp_c`; `oximetry` → `spo2_pct` |
| `smart_clothing` | `motion` → `accel_x`, `accel_y`, `accel_z`; `respiration` → `breathing_rpm` |
| all | `ingestion` → `last_message_id`, `last_seq`, `last_run_id`, `last_ts`, `accepted_count` |

Idempotency (plan §5.4), **scoped per run** (v1.1): reject a repeated
`message_id` (per-device LRU; the `message_id` values are UUID v5 of
`run_id:device_uuid:seq`, so they are already unique per run) and reject
`seq` ≤ the known `last_seq` **only within the same `run_id`**. When an event's
`run_id` differs from the device's `last_run_id`, the `seq` floor is reset
(new runs restart `seq` at 0 — the case of the 10 consecutive `smoke` runs
and of the warm-up that precedes each measured run). The state (`ingestion`,
including `last_run_id`) lives in the twin so that it survives controller
restarts; the local cache is rebuilt by reading the twin on the first event
from each device after start-up.

*Rationale (v1.1):* without per-run scoping, the harness warm-up (same seed →
same `device_uuid`s) would raise the `seq` floor and cause the first messages
of each measured run to be rejected as duplicates, corrupting the delivery
rate.

## 5. Controller (MQTT→Ditto bridge)

- Asynchronous MQTT subscription (QoS 1); JSON Schema validation **before** any
  call to Ditto; conversion to merge-patch and `PATCH /api/2/things/{thingId}`
  (`content-type: application/merge-patch+json`); creation of policy+thing on
  the first event from a `device_uuid`.
- **`message_id` verification** (section 2), after schema validation and
  **before** consulting the idempotency cache and before seeding or patching
  any twin: the controller recomputes the UUID v5 of
  `run_id:device_uuid:seq` and rejects any divergence (`outcome: rejected`,
  with no call to Ditto whatsoever). The schema only proves the *shape* of a
  UUID v5; without this check any producer could submit an arbitrary but
  well-formed identifier and defeat the duplicate detection of section 4,
  which assumes `message_id` is a pure function of those three fields.
- Bounded retry (default 3 attempts, exponential backoff with 200 ms base) only
  for transient errors (timeout, 5xx, connection); 4xx is not retryable.
- Structured JSON logging on stderr; counters: `accepted`, `rejected`,
  `duplicate`, `failed`.
- HTTP endpoints (port `8000`):
  - `GET /health` → `{"status":"ok"}` (process alive);
  - `GET /ready` → 200 only with MQTT connected and Ditto reachable; 503 otherwise;
  - `GET /twins/{device_id}` → normalised twin read;
  - `GET /metrics` → counters + uptime + confirmation marker (JSON):
    `accepted`, `rejected`, `duplicate`, `failed`, `dropped`, `queue_depth`,
    `started_at`, `uptime_s`, `monotonic_ns` (integer) and `wall_utc`
    (RFC 3339 UTC). The last two are additive (v1.1 → P5) and change no
    existing field.

### Confirmation marker in `GET /metrics` (additive, sprint P5)

`monotonic_ns` = `time.monotonic_ns()` read **while handling the request**;
`wall_utc` = the same instant on the wall clock (RFC 3339 UTC, `Z` suffix).

- **What it is:** a temporal anchor in the **controller's clock domain** —
  the same process, hence the same monotonic clock as
  `received_monotonic_ns` / `ditto_ack_monotonic_ns` in `events.jsonl`. The
  harness reads it **immediately after the measured simulator process ends and
  before the confirmation wait**, and records in the manifest
  `controller_monotonic_at_run_end_ns`,
  `confirmation_deadline_monotonic_ns` (= marker + `confirmation_window_s`
  in ns) and `confirmation_deadline_clock_domain: "controller"`.
- **Why it is not the latency clock:** the primary latency remains
  `latency_ms = (ditto_ack_monotonic_ns − received_monotonic_ns)/1e6`,
  computed in the same process per message (section 9). The marker never
  enters the latency calculation, nor does it replace either of the two
  timestamps; it is merely the **end-of-run** instant projected onto the
  controller's clock.
- **Why it is needed:** without it the confirmation deadline would have to be
  derived from the events themselves (e.g. `max(received_monotonic_ns)` + window),
  which is circular — a message received late would shift its own deadline
  and could never be counted as lost.
- **The 60 s rule does not change:** the confirmation window remains
  `confirmation_window_s` (default 60 s, section 9 and plan §7.3); only the
  **end instant** is no longer inferred from the events.
- **Unavailability:** if the controller cannot be queried, the manifest
  records `confirmation_deadline_monotonic_ns: null`,
  `confirmation_deadline_clock_domain: "unavailable"` and a
  `confirmation_marker_unavailable` deviation; under the timed conditions the
  run becomes `invalid` unless
  `--allow-missing-controller-marker` is passed (which records the deviation
  instead of invalidating). The analysis then falls back to the deadline
  derived from the events, marking the run as legacy/non-verifiable with an
  explicit warning and recording `confirmation_deadline_source` in `per_run.csv`.

### Event log (primary latency source — plan §5.8/§7.3)

The controller writes `events.jsonl` (one per `run_id`, in `EGW_EVENT_LOG_DIR`):

```json
{"run_id":"...","message_id":"...","device_uuid":"...","device_type":"...",
 "seq":0,"received_monotonic_ns":0,"ditto_ack_monotonic_ns":0,
 "latency_ms":0.0,"outcome":"accepted|rejected|duplicate|failed",
 "attempts":1,"error":null}
```

- `received_monotonic_ns`: `time.monotonic_ns()` in the MQTT callback;
- `ditto_ack_monotonic_ns`: after a 2xx response from Ditto;
- `latency_ms = (ditto_ack - received)/1e6`, computed in the same process;
- `rejected`/`duplicate`/`failed` have `ditto_ack_monotonic_ns` and `latency_ms` set to `null`.

## 7. Simulator — reference CLI (plan §5.6)

```text
python -m egw_simulator run --scenario nominal --seed 42 \
  --broker <host> --port 8883 --duration 600 --rate 11.2 --output <dir> \
  [--devices smartwatch,smart_ring,smart_clothing] [--egw-id egw-01] \
  [--run-id <id>] [--username u --password p --ca-cert ca.crt | --no-tls] [--qos 1]
```

- Scenarios: `smoke`, `nominal`, `load-sweep`, `dropout-reconnect`,
  `invalid-payload`, `soak`.
- Determinism: same seed ⇒ same sequence of payloads (per device).
- Local validation of every payload before publishing, except the intentionally
  invalid events of `invalid-payload`, which are flagged in the simulator's
  log (`intended_invalid: true`), never in the payload.
- Output per run: `manifest.json` (scenario, seed, commit, config, timestamps,
  protocol version) + `sent_events.jsonl`
  (`{run_id, message_id, device_uuid, device_type, seq, publish_monotonic_ns, puback_monotonic_ns, intended_invalid}`).
  *(v1.1: `device_type` added — enables per-type analyses without a join against the manifest.)*
- Capture of `puback_monotonic_ns` is *best-effort*: the wait for the PUBACK is
  limited to the free time until the next scheduled event (it never blocks the
  publication pace); `null` when the PUBACK was not observed in time. The
  primary metrics (plan §7.3) never depend on this field.

## 9. Metrics and statistical definitions (plan §7.3)

`sent` = handed to the MQTT publish; `received` = controller callback;
`duplicate` = `message_id` already processed; `rejected` = validation failure;
`confirmed` = 2xx from Ditto; `lost` = valid message sent without a unique
confirmation within 60 s after the end of the run. Delivery rate = unique
confirmations / valid messages sent. Statistical unit = the run, never the
message. Primary latency = the controller's `latency_ms` (p50/p95/p99).
