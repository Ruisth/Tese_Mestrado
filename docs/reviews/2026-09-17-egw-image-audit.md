## 1. Verdict

**Answer: not yet.** The sealed `egw-image` (gate G1, `docs/evidence/g1-yocto-qemu/2026-08-14-clean-build-f0e19d5/`) is a sound container-host foundation, but it is a Poky default-features image, not a purpose-built gateway, and it cannot host the six-container stack of ADR 0008 as it stands. Nothing was built or booted for this audit; every figure below was read from the sealed evidence, the G1 build tree in WSL (`/home/ruisth/yocto/egw/src/yocto`) or the repository, and the G1 inputs are untouched.

1. **What is right.** linux-yocto 6.6.142 carries every container feature Docker needs (`CONFIG_OVERLAY_FS`, `CONFIG_MEMCG`, `CONFIG_CGROUP_PIDS`, `CONFIG_USER_NS`, `CONFIG_SECCOMP_FILTER`, `CONFIG_BRIDGE`, `CONFIG_VETH` = y; `CONFIG_NF_NAT`, `CONFIG_IP_NF_NAT`, `CONFIG_IP_NF_TARGET_MASQUERADE`, `CONFIG_NETFILTER_XT_MATCH_ADDRTYPE`, `CONFIG_NETFILTER_XT_MATCH_CONNTRACK` = m and installed); docker-moby 25.0.9 with containerd, runc and tini ran with `overlay2` and the systemd cgroup driver in the sealed boots (`qemu-g1r2-01.log`); systemd 255.21 supplies networkd DHCP, resolved DNS and timesyncd, all enabled; OpenSSH with `sftp-server`, `openssl-bin` and `ca-certificates` are present. The OCI runtime is 181.8 MiB of the 309.9 MiB of installed packages (58.7 %) and must stay.
2. **What is bloat, and how small it is.** Packages that come only from Poky's default `DISTRO_FEATURES`/`MACHINE_FEATURES` — bluez5 with its glib chain, shared-mime-info + libxml2, the X11 client libraries, kbd, alsa, avahi, rpcbind, dosfstools, locales — total **24.3 MiB (7.8 %)**; the kernel `Image` installed a second time inside the rootfs (`/boot/Image-6.6.142-yocto-standard`, 24,150,528 B = 23.0 MiB, never read because runqemu passes `-kernel`) adds **7.4 %**; `udev-hwdb` (8.4 MiB, 2.7 %) is optional. About 47 MiB (15 %) is certainly removable, 56 MiB (18 %) at most. The gain is cleanliness and exposure, not disk space: `avahi-daemon`, `rpcbind` (111/tcp+udp) and `bluetooth.service` are enabled for no purpose, and `debug-tweaks` leaves root with an empty password, `PermitRootLogin yes` and `PermitEmptyPasswords yes` (`sshd_config` lines 34 and 60 in the G1 rootfs).
3. **What is missing.** The Compose V2 plugin (every deployment script calls `docker compose`); `curl` (`measure-cold-start.sh` line 74); a non-root operator with uid 1000, key-only SSH and `sudo`; a persistent, size-capped journal (`/var/log` is a symlink into tmpfs); an explicit NTP configuration (`timesyncd.conf` has an empty `[Time]` section); `/etc/docker/daemon.json`; an event directory writable by uid 1000; storage for the six images, the MongoDB volume and the logs (the root ext4 has 2 GiB of headroom and `resize2fs` is not installed); a guest identity other than the hostname `qemuarm64`.
4. **What blocks running the stack.** The sealed QEMU profile (`image-qemuboot.conf`: `qb_cpu = -cpu cortex-a57`, `qb_mem = -m 256`, from which runqemu also derives the kernel argument `mem=256M`) cannot start MongoDB 7, which the vendor supports on arm64 only from ARMv8.2-A, and gives 256 MiB to a stack whose compose memory limits alone sum to 2,432 MiB; without Compose nothing starts; `compose.yaml` lines 210–212 still build the controller inside a guest that has no pip, git or buildx, so the controller must be prebuilt off-guest and loaded from a checksummed archive, with identity proven by image ID because `docker load` never restores a `RepoDigest`.
5. **What blocks a VM or cloud boot.** The build deploys a bare kernel `Image` (24,150,528 B), an unpartitioned `rootfs.ext4` (2,607,275,008 B) and a `tar.bz2` (92,693,208 B): no GPT, no EFI System Partition, no boot loader (`EFI_PROVIDER` unset, `IMAGE_FSTYPES = "tar.bz2 ext4"`), so only a hypervisor that injects the kernel (runqemu) can start it; and the qemuarm64 kernel has `# CONFIG_ACPI is not set`, `# CONFIG_BLK_DEV_NVME is not set` and `# CONFIG_ENA_ETHERNET is not set`, so an ACPI/NVMe/ENA platform such as AWS Graviton would have neither root disk nor network.

The proposed change set (new recipes `egw-gateway-image`, `egw-gateway-config`, manifests `kas/egw-qemuarm64-integrated.yml` and `kas/egw-genericarm64.yml`) addresses the image-side points (items 2, 3 and 5, and the CPU, RAM and Compose parts of item 4) on paper; the controller prebuild, the removal of the `build:` stanza, the image references for loaded archives and the README path alignment are deployment-PR work that this change set does not contain (it holds nothing under `src/deployment`). It becomes true only when the student builds and boots it; until then every behaviour described in this report is an expectation.

### 5.1 What the profile is, and the label it must carry

The profile is a second kas manifest for the **same machine** as G1 (`MACHINE = "qemuarm64"`, same three pinned commits, same shared download/sstate caches) that builds a **different image** (`egw-gateway-image`) in a **different build directory** and writes a different runqemu profile into the image's `qemuboot.conf`. Mandatory label (runbook `docs/setup/qemu_integrated_gateway.md` §0; PM item 1; ADR 0008), to be used in the evidence README, `sut_environment.json`, run manifests, figures and dissertation text:

> ARM64 **emulated** by QEMU 8.2.7/TCG on an x86-64 host (Windows 11, WSL2 Ubuntu-24.04). Never native ARM64, never KVM.

The x86 KVM of the WSL2 kernel cannot accelerate an aarch64 guest, so `QB_CPU_KVM` (inherited from `qemuarm64.conf`) is unused here. ### 5.3 PM item 2 — CPU model

- `QB_CPU:qemuarm64 = "-cpu cortex-a76"` (ARMv8.2-A). The sealed G1 profile used `-cpu cortex-a57` (ARMv8.0-A), and MongoDB 7 on arm64 requires ARMv8.2-A (vendor production notes, quoted in plan v2.0); this is why the full stack was never runnable in the G1 configuration (`verified_facts.md`).
- Verified in the build tree: poky's `qemu-system-native` 8.2.7 lists `cortex-a57, cortex-a76, neoverse-n1, neoverse-n2, neoverse-v1, max` (`target/arm/tcg/cpu64.c` line 1266 for `cortex-a76`; `hw/arm/virt.c` line 214 accepts it for `-machine virt`).
- `cortex-a76` rather than `max`: `max` is not a real core, so evidence would describe a CPU that exists nowhere; `cortex-a76` is the model poky's own `genericarm64.conf` uses and the core of the Raspberry Pi 5 named in the plan.
- The `:qemuarm64` override is **required**, not cosmetic: `bitbake.conf` includes `local.conf` before `conf/machine/qemuarm64.conf`, which assigns `QB_CPU` (line 17) and `QB_OPT_APPEND` (line 22) with a plain `=`.
- `QB_SMP:qemuarm64 = "-smp 4"` (the G1 value; QEMU 8.2.7 runs AArch64 guests with multi-threaded TCG). `QB_OPT_APPEND:qemuarm64 = ""` drops the USB HID devices of the graphical console.
- Acceptance (runbook §3.4-§3.5): `grep '^CPU part' /proc/cpuinfo` → `0xd0b`; `nproc` → 4; `mongod` starts and logs `Waiting for connections` with no SIGILL. **Unverified:** the `0xd0b` part number and the feature flags are general Arm knowledge, not read from a document in the checkout; that MongoDB 7 actually starts under this TCG model is the decisive first-boot test.

### 5.4 PM item 2 — memory, and how `mem=` follows

The old tests pass `-m 256` and `mem=256M` together. The work order's concern — changing one and leaving Linux capped by the other — does not arise if memory is set where runqemu expects it. Re-read in WSL for this report, `poky/scripts/runqemu` `check_mem()` (lines 818-845):

1. if `qemuparams` contains `-m N`, `QB_MEM` is set from it; otherwise an unset `QB_MEM` defaults to `-m 256`;
2. for every machine whose name does not start with `qemumips`, `qemux86` or `qemuloongarch64`, ` mem=<N>M` derived from `QB_MEM` is appended to the kernel command line (line 843);
3. `QB_MEM` itself is appended to the QEMU options (line 845).

So `QB_MEM = "-m 8192"` in block `50-qemu-profile` yields both `-m 8192` and `mem=8192M`; a per-run `EGW_QEMU_EXTRA="-m 6144"` (passed through `qemuparams`) also moves both. The runbook forbids passing `mem=` by hand through `bootparams=` (§3.3). Acceptance inside the guest (§3.4): `cat /proc/cmdline` shows `mem=8192M`, `MemTotal` is consistent with it, `free -m`.

Sizing rationale: the compose memory limits sum to 2,432 MiB (mosquitto 128 + mongodb 512 + 3 × Ditto 512 + controller 256), plus dockerd/containerd, the kernel, page cache and three JVMs starting under emulation. 4 vCPU / 8 GiB is the work order's **starting point, not a guarantee**: it is to be validated in the pilot. Host headroom (checked read-only on 2026-09-18): the workstation has about 64 GiB of physical memory (63.4 GiB reported by Windows), no `%UserProfile%\.wslconfig` exists, and the WSL2 VM therefore receives the 50 % default — 31 GiB (`free -g`). No `.wslconfig` change is needed for an 8 GiB guest; if a `[wsl2] memory=` limit is ever set it must stay at 20 GB or more. Still required: `free -g` before each boot, and no BitBake build while the guest is up. Runbook §1.3 words this as "the host has 31 GiB" and asks for `memory=20GB`, which would lower the current allocation; that wording is listed as a residual defect (Section 10, E7).

### 5.5 PM item 2 — storage: a second, persistent data disk

| Disk | Content | How it is sized |
|---|---|---|
| Root (`vda`): the deployed `egw-gateway-image-qemuarm64.rootfs.ext4`, booted **in place** by runqemu (no `-snapshot`) | OS, `/opt/egw` (deployment tree, `data/events`, evidence), `/home/egw`, journal capped at 256 MiB | `IMAGE_ROOTFS_EXTRA_SPACE = "2097152"` (2 GiB, the G1 value); never grown |
| Data (`vdb`): `$HOME/yocto/egw-integrated/egw-data.img`, label `egw-data`, mounted on `/var/lib/docker` | Image layers (overlay2), the `mongodb-data` and `mosquitto-data` named volumes, json-file container logs (50 MiB × 3 per container, `daemon.json`) | 32 GiB sparse by default (`EGW_DATA_DISK_SIZE`); grow with `truncate -s 64G` on the host, the guest resizes at next boot |

Why a second disk rather than a larger root: container state written into the root file system would sit inside a build artefact and be overwritten by every rebuild; one file can be sized, grown, reset (delete or rename it — the destructive reset "limited to identified test volumes" of PM item 8) and checksummed independently; and guest-reboot tests then exercise real persistence.

Mechanism, three parts:

- **Host:** `run-qemu-integrated.sh` creates the file (`truncate` + `mkfs.ext4 -q -F -L egw-data`), checks the label with `blkid`, and attaches it per run with `qemuparams="-drive id=disk1,file=<abs path>,if=none,format=raw -device virtio-blk-pci,drive=disk1"`. It is attached per run rather than through `QB_OPT_APPEND` because `qemuboot.conf` is written at build time and runqemu substitutes only `@DEPLOY_DIR_IMAGE@` there.
- **Guest, fstab:** `egw_add_data_disk_fstab` appends `LABEL=egw-data  /var/lib/docker  ext4  defaults,nofail,x-systemd.growfs,x-systemd.device-timeout=30s  0  0`. An fstab line is used instead of a `.mount` unit because `systemd-fstab-generator` turns `x-systemd.growfs` into `systemd-growfs@var-lib-docker.service` (systemd 255.21 `fstab-generator.c` lines 659-660, 806).
- **Guest, ordering:** the `docker.service` drop-in `10-egw-data-disk.conf` sets `RequiresMountsFor=/var/lib/docker`, so without the disk dockerd **fails visibly** (`systemctl --failed`) instead of silently filling the root; boot and SSH continue (`nofail`).

Consequences recorded in the runbook (§3.2): the sha256 of the root `.ext4` taken at build time identifies the artefact *before its first boot only*; runqemu adds `-no-reboot` for ext4 roots, so a guest `reboot` ends QEMU and the wrapper is run again with the **same** data-disk file (integration test 8). All of the systemd behaviour above is inferred from source, not booted.

### 5.6 PM item 5 — port forwarding and loopback-only APIs

`QB_SLIRP_OPT = "-netdev user,id=net0,hostfwd=tcp:127.0.0.1:2222-:22,hostfwd=tcp:127.0.0.1:8883-:8883"`. `QB_SLIRP_OPT` **replaces** runqemu's whole default netdev string (`setup_slirp`, lines 1107-1145), so both forwards are stated; the default `2323->23` (no telnet daemon) and `tftp=` are dropped. Both listeners bind to the host's `127.0.0.1` only.

- `2222 -> 22`: operator SSH, `scp`, and `ssh -L` tunnels to the controller (`:8000`) and the Ditto gateway (`:8080`). `compose.yaml` binds those two to `127.0.0.1` **inside the guest**, and forwarding a port to the guest NIC does not expose a loopback-bound service — hence tunnels (runbook §5.7), not more `hostfwd` entries.
- `8883 -> 8883`: MQTT/TLS. `compose.yaml` publishes Mosquitto on all guest interfaces; the simulator connects to `127.0.0.1:8883` on the host with the dev CA. `generate-dev-tls.sh` takes **no positional argument** and its default SAN already contains `IP:127.0.0.1`, so certificate verification stays on with no extra option (runbook §5.3, §6.2).
- MongoDB (27017) and the Ditto devops interface are not forwarded.
- runqemu silently re-maps a busy host port and logs `Port forward changed: 8883 -> 8884`. The wrapper warns beforehand (`ss -ltn`), and the runbook requires reading the actual mapping from the log after every boot (§3.1, §3.3).

### 5.8 PM item 3 — SSH and the operator account

- Account `egw`, uid/gid 1000, member of `docker`, shell `/bin/sh`, created by `EXTRA_USERS_PARAMS`. **Uid 1000 is the uid the controller container runs as** (`src/Dockerfile`: `useradd --uid 1000`), so the deployment tree and the `data/events` bind mount are owned by the right uid without a `chown` step.
- Password field `-p '*'`: round 1 found (blocker) that `useradd` without `-p` writes `!`, and poky's OpenSSH 9.6p1 is built with `LOCKED_PASSWD_PREFIX "!"` and without PAM (`config.h` line 1709; `platform.c` lines 245-247; `auth.c` line 112), so sshd would refuse the account **even with a valid key**. `*` is unusable but not locked. Build acceptance: `tar -xjOf …rootfs.tar.bz2 ./etc/shadow | grep ^egw:` prints `egw:*:` (runbook §2.4) — if it shows `!`, do not boot.
- Public key: read at build time from the file named by the environment variable `EGW_AUTHORIZED_KEYS_FILE` (declared in the manifest's `env:` block; kas hands it to BitBake through `BB_ENV_PASSTHROUGH_ADDITIONS`). The key is never stored in the layer; a file containing `PRIVATE KEY` is refused; `do_rootfs[file-checksums]` re-runs the rootfs when the key's content changes. With `EGW_AUTHORIZED_KEYS_REQUIRED = "1"` the campaign image **fails its build** when the variable is empty — an image with key-only SSH and a locked root would otherwise be silently unreachable. No key, certificate or password is committed anywhere in the change set (scanned for this report: no `PRIVATE KEY` block and no public-key material).
- sshd drop-in `/etc/ssh/sshd_config.d/10-egw.conf`: `PermitRootLogin no`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitEmptyPasswords no`, `AllowUsers egw`, `X11Forwarding no`, keep-alives for the long-lived tunnels. poky's `sshd_config` has `Include /etc/ssh/sshd_config.d/*.conf` on line 13, before every default, and sshd keeps the first value of a keyword.
- Root: without `debug-tweaks`, `zap_empty_root_password` locks it (`root:*:`).
- `sudo`: `/etc/sudoers.d/egw` = `egw ALL=(ALL:ALL) NOPASSWD: ALL`, with a narrower rule given in the file's comments for the campaign. **`UNVERIFIED:`** that poky's sudo 1.9.17p2 installs a `sudoers` with an active `@includedir /etc/sudoers.d` (sudo was never built in this tree), and that sudo built `--without-pam` honours `NOPASSWD`; first-boot acceptance `sudo -n true`, `visudo -c`, `sudo -l -U egw`.
- `egw-gateway-image-dev.bb` = `require egw-gateway-image.bb` + `debug-tweaks` + `egw-container-smoke` + `EGW_AUTHORIZED_KEYS_REQUIRED = "0"`. Root console login for bring-up; the sshd drop-in is predicted to keep root refused over SSH (untested). QEMU/slirp only, never an evidence image; the artefact names carry `-dev` so the two cannot be confused.

### 6.4 Rules against weakening validations

1. **No bypass flags.** The harness has `--allow-missing-sut-env`, `--allow-missing-resources` and `--allow-missing-controller-marker` (`src/egw_experiments/cli.py` lines 129-141). None is used to make an integration or pilot run pass (RB §8 rule 5). Missing `sut_environment.json`, missing or short `resources.csv`, collector hook failures and checksum mismatches still invalidate a run.
2. **Slowness is not an exclusion criterion.** A slow run under TCG is a finding. If `lost > 0` appears at 11.2 msg/s, that is the first sizing result of the pilot, not a reason to change the protocol (RB §7 test 1).
3. **Timing changes only in a documented profile.** Start-up timeouts may be raised in `compose.tcg.yaml` and a named harness profile, recorded in the evidence. The 60 s confirmation window (CONTRACTS §9), the loss criteria, the saturation rules and `RESTART_RECOVERY_MAX_S` do not change, silently or otherwise.
4. **Architecture checks stay.** `generate-runtime-lock.sh` keeps refusing non-aarch64 hosts; an x86 lock is never accepted. A MongoDB SIGILL is fixed by the CPU model, never by relaxing an image's architecture check (RB §3.5).
5. **Identity before use.** An image whose guest `.Id` does not match `archive-identity.txt` is not run (RB §4.4).
6. **TLS verification stays on.** `--no-tls` appears only as a negative test (test 9c); the simulator has no insecure-TLS option.
7. **Run identifiers cannot collide with the campaign.** `itest-` prefixes and a pilot plan in `~/egw-tcg/pilot/`; `experiments/campaign_plan.json` is never used on this environment.

### 6.5 Pilot before campaign; supervisor agreement

Order fixed by RB §8, entered only after tests 1-9 pass: one short nominal run (120 s) → the plan's nominal duration (600 s) → `load-sweep` at 10 and 50 msg/s (300 s each) → a short soak (3,600 s). On every run the achieved rate (`sent / duration` from `sent_events.jsonl`) is compared with the requested rate; if the generator cannot sustain it, the run is a pilot finding, not a measurement. QEMU/TCG (four vCPU threads plus I/O), the simulator, the harness sampler and the SSH tunnels share the WSL2 VM's 16 CPUs and memory limit: that competition is documented with each run, and no Yocto build, Windows sleep/hibernate or Docker Desktop build happens during a run.

**Not started on this environment:** the 24 h soak and the 95 runs of `experiments/campaign_plan.json`.

**Supervisor agreement is a precondition, not a formality.** ADR 0008 (line 19) states that QEMU/TCG emulation on the x86-64 WSL host "remains useful for functional checks and contributes no ARM hardware performance result". Numbers produced here characterise this emulated configuration only; whether, and how, they may appear in the dissertation (functional evidence, a rehearsal of the procedure, or labelled measurements of an emulated configuration) must be agreed with the supervisors **before** any of them is used (PM item 9 and the work order's final criterion). The native route (`kas/egw-genericarm64.yml`, RB §10) remains the path to admissible RQ3 timings, and RB §4-§7 are written to run unchanged on it.

## 7. Boot targets and the native route (second deliverable)

The PM work order of 2026-09-17 makes the integrated QEMU/TCG gateway the first deliverable because no ARM64 VM could be obtained; the native ARM64 route is the *subsequent* step. This section records why today's artefacts cannot be uploaded anywhere, what each candidate target needs, and what the native-route files of the change set finally contain. **Nothing on this route has been built or booted.** The only boots that exist are the five sealed G1 runs under runqemu on the x86-64 WSL2 host with `-cpu cortex-a57` and `-m 256`, without the container stack; every status below is therefore an expectation derived from reading recipes, kernel configuration and vendor pages, and "works" is reserved for configurations with an archived boot log — there is none beyond G1.

### 7.1 Why the current artefacts are not a bootable disk

- **What is deployed** (`build/tmp/deploy/images/qemuarm64/`, listed 2026-09-18): `Image` (24,150,528 B), `egw-image-qemuarm64.rootfs.ext4` (2,607,275,008 B, of which 2 GiB is `IMAGE_ROOTFS_EXTRA_SPACE`), `.tar.bz2` (92,693,208 B), a modules `.tgz`, and metadata. `IMAGE_FSTYPES` is `tar.bz2 ext4` (appended by `poky/meta/conf/machine/include/qemu.inc`); the `testdata.json` in the G1 build tree's deploy directory (`egw-image-qemuarm64.rootfs-20260811210857.testdata.json`; not part of the sealed evidence) has `EFI_PROVIDER` unset and `WKS_FILE = egw-image.qemuarm64.wks`, a file that exists in no layer. There is no `.wic`, no partition table, no EFI System Partition and no boot loader.
- **How it boots today.** runqemu injects the kernel: `-kernel Image`, the raw ext4 as a virtio-blk disk (`QB_ROOTFS_OPT` in `qemuarm64.conf`), `root=/dev/vda` on the command line. UEFI firmware — the only boot mode of AWS Graviton instance types according to the AWS boot-mode documentation (`ami-boot.html`), and the norm for ARM64 cloud VMs — scans a GPT disk for an ESP and an EFI loader; a bare ext4 file offers neither, and `register-image` accepts only a whole-disk snapshot. The kernel does have `CONFIG_EFI=y`, `CONFIG_EFI_STUB=y` and `CONFIG_EFI_PARTITION=y`, so it *could* be started as an EFI application, but nothing places it on an ESP with a loader entry.
- **What the kernel lacks** (qemuarm64 `.config`, linux-yocto 6.6.142, `KBRANCH v6.6/standard/qemuarm64`): `# CONFIG_ACPI is not set`, `# CONFIG_BLK_DEV_NVME is not set`, `# CONFIG_ENA_ETHERNET is not set`, and also `CONFIG_ARM_SMMU_V3`, `CONFIG_SERIAL_8250`, `CONFIG_RTC_DRV_EFI` and `CONFIG_XFS_FS` unset. Present and sufficient for a QEMU `virt` guest: all virtio front-ends, `CONFIG_PCI_HOST_GENERIC=y`, `CONFIG_ARM_GIC_V3=y`, `CONFIG_SERIAL_AMBA_PL011=y`, `CONFIG_RTC_DRV_PL031=y`. On a Nitro instance EBS volumes are NVMe devices and the network is ENA (AWS documentation, `nvme-ebs-volumes.html`, `enhanced-networking-ena.html`): this kernel would find neither root disk nor NIC.
- **Security.** `debug-tweaks` (passwordless root, `PermitRootLogin yes`, `PermitEmptyPasswords yes`) is tolerable behind slirp on a workstation and unacceptable on an instance with a public address that must expose 8883.

### 7.4 What the native-route files finally contain

After two adversarial rounds (`round2/files_native-route.json`, `round2/fix_native-route.json`). All of it is a proposal to build later.

- **`src/yocto/kas/egw-genericarm64.yml`** (+ `.lock.yml`, same three pins as G1). MACHINE `genericarm64`; adds the `meta-yocto-bsp` layer of the pinned poky; targets `egw-gateway-image` and `u-boot`. u-boot (`UBOOT_MACHINE = "qemu_arm64_defconfig"`) is *only* the firmware runqemu loads for this machine (`QB_DEFAULT_BIOS = "u-boot.bin"`, `QB_DEFAULT_KERNEL = "none"`); it is never written to the disk, and real platforms bring their own UEFI. The build directory is selected with the environment variable `KAS_BUILD_DIR=$PWD/build-genericarm64` — read by kas 5.4 in `kas/context.py` line 85; it is not a command-line option, so `kas build --help` does not list it, and `scripts/build.sh` cannot pass it (use `scripts/build-profile.sh genericarm64`).
  - *Feature trim*: `DISTRO_FEATURES:remove = "alsa bluetooth wifi 3g nfc pcmcia usbgadget usbhost x11 wayland opengl vulkan pulseaudio nfs zeroconf ptest debuginfod"` (the last two are build-time only); `MACHINE_FEATURES:remove = "acpi alsa bluetooth efi keyboard screen usbhost wifi"`; the Wi-Fi/Realtek firmware is dropped from `MACHINE_EXTRA_RRECOMMENDS`. Removing the `acpi` *feature* removes only `acpid`; the kernel keeps `CONFIG_ACPI=y`. Removing `efi` stops `packagegroup-core-boot.bb` line 29 from installing systemd-boot and the `kernel` meta-package under the rootfs `/boot`, which the ESP is mounted over; its only other consumers in the pinned layers are `linux-yocto.inc` line 36 (the `cfg/efi.scc` kernel feature, neutralised because the BSP includes `cfg/efi-ext.scc` and `egw-vm.cfg` restates `CONFIG_EFI`, `CONFIG_EFI_STUB`, `CONFIG_EFIVAR_FS`), `live-vm-common.bbclass` (not inherited) and meta-oe's fwupd (not built). On this BSP Bluetooth and sound are *kernel* features (`features/bluetooth/bluetooth.scc`, `cfg/sound.scc`), unlike qemuarm64 where `CONFIG_BT` and `CONFIG_SOUND` are unset: the modules will be built, only the userspace stays out.
  - *Initramfs*: `PACKAGE_INSTALL:remove:pn-core-image-initramfs-boot = "kernel-modules"` — virtio, NVMe, the PCI host bridge and ext4 are built in, and the genericarm64 BSP builds far more modules than qemuarm64, which would otherwise be packed both into the rootfs and into the `cpio.gz` on the ESP. **Untested**: if the guest cannot find its root device, drop this line first.
  - *Image outputs*: `IMAGE_FSTYPES = "wic wic.bmap tar.bz2"`; `WKS_FILE = "egw-genericarm64.wks.in"` set in the manifest so that the image recipe stays machine-agnostic; `EFI_PROVIDER = "systemd-boot"`; `WKS_FILE_DEPENDS:append = " systemd-boot"`, required because `image_types_wic.bbclass` lines 112–115 add the loader to the wic dependencies for x86 only. Mechanism traced (`systemd-boot_255.21.bb` `do_deploy`; `do_image_wic[recrdeptask]`; `bootimg-efi.py` lines 424–426 copy `systemd-bootaa64.efi` to `EFI/BOOT/bootaa64.efi`) but never exercised.
  - *Storage — two disks, no growth mechanism.* The first draft's `systemd-repart` + `x-systemd.growfs` root growth was **removed**: nothing in the final change set ships a `repart.d` definition (without one `systemd-repart.service` is skipped by its `ConditionDirectoryNotEmpty=` lines), nothing edits the `/` line of fstab, and systemd's `repart` PACKAGECONFIG is not enabled. The root partition is sized at build time from `ROOTFS_SIZE` (`image.bbclass` `get_rootfs_size`, lines 541–570: `du` × 1.3 + 2 GiB of `IMAGE_ROOTFS_EXTRA_SPACE`, about 2.5 GiB) and never grown; a larger OS volume leaves its tail unused. `/var/lib/docker` lives on a **second** ext4 block device labelled `egw-data` (`EGW_DOCKER_DATA_DISK = "1"`), exactly as in the integrated profile; without it `docker.service` ends as "Dependency failed" after the 30 s device timeout while boot and SSH continue. On a KVM host the disk is formatted on the host; on a cloud VM a blank volume is formatted once from the guest (`sudo mkfs.ext4 -L egw-data /dev/<device>`), which is why this manifest — and only this one — adds `e2fsprogs-mke2fs` to `egw-gateway-image`. The plan's own warning ("do not assume automatic online expansion", §4) is thereby respected rather than worked around.
  - *Other settings*: `PACKAGECONFIG:remove:pn-systemd = "vconsole"`; `VIRTUAL-RUNTIME_base-utils-syslog = ""`; `BAD_RECOMMENDATIONS += "shared-mime-info dosfstools"` (`udev-hwdb` commented, optional); `EGW_PERSISTENT_VAR_LOG = "1"` (the image's `egw_persistent_var_log` post-process; the global `VOLATILE_LOG_DIR` is left untouched so that both profiles share one mechanism); `EGW_DOCKER_DATA_DISK_LABEL = "egw-data"` (beside `EGW_DOCKER_DATA_DISK = "1"`, see *Storage* above); `EGW_HOSTNAME = "egw-genericarm64"` (written to `/etc/hostname` and `/etc/hosts` by `egw_set_hostname` in `egw-gateway-image.bb` and recorded in `/etc/buildinfo`; the `hostname:pn-base-files` override is deliberately not used), deliberately different from `egw-qemu-integrated`; a commented `EGW_NTP_SERVERS = "169.254.169.123"` for AWS; `QB_MEM = "-m 6144"` and the same `QB_SLIRP_OPT` (2222→22, 8883→8883) for a functional runqemu check. With `QB_DEFAULT_KERNEL = "none"` runqemu passes no `-append`, so there is no second `mem=` value to keep in step on this machine.
  - *One residual inconsistency, harmless but worth tidying when the route is built*: `QB_MEM` is `-m 6144` here, whereas the integrated profile settled on `-m 8192`.
- **`src/yocto/meta-egw/recipes-kernel/linux/linux-yocto_%.bbappend`.** `SRC_URI:append:genericarm64 = " file://egw-vm.cfg"` and `RRECOMMENDS:${KERNEL_PACKAGE_NAME}-base:genericarm64 = ""` (keeps the 23.0 MiB `Image` package out of the rootfs). The only line without the `:genericarm64` override is `FILESEXTRAPATHS:prepend`, which is in `BB_HASHEXCLUDE_COMMON` (`bitbake.conf` line 954), so the qemuarm64 kernel's task signatures are unchanged — provable before any build with `bitbake -S none linux-yocto` and `bitbake -e linux-yocto | grep '^SRC_URI='` in the G1 build directory.
- **`…/linux/files/egw-vm.cfg`** — 19 symbols, each located in the 6.6.142 source (both the built qemuarm64 tree and commit a8a7d078 in the download-cache mirror) with its Kconfig dependencies satisfiable:
  - storage `CONFIG_NVME_CORE=y`, `CONFIG_BLK_DEV_NVME=y` (depends on `PCI && BLOCK`);
  - network `CONFIG_NET_VENDOR_AMAZON=y`, `CONFIG_ENA_ETHERNET=y` (depends on `PCI_MSI && !CPU_BIG_ENDIAN`);
  - `CONFIG_PCI_HOST_GENERIC=y` (`=m` in `genericarm64.cfg`), so PCI devices exist before any module loads;
  - clocks `CONFIG_EFIVAR_FS=y`, `CONFIG_RTC_DRV_EFI=y` (a hypothesis for Nitro) and `CONFIG_RTC_DRV_PL031=y` — the qemuarm64 value does **not** carry over, since no fragment under `bsp/genericarm64/` sets it and the QEMU `virt` functional check would otherwise have no RTC driver;
  - console `CONFIG_SERIAL_8250=y`, `CONFIG_SERIAL_8250_CONSOLE=y`, `CONFIG_SERIAL_8250_PCI=y` (the BSP sets `=m` in `genericarm64-serial.cfg` and `=y` through `cfg/8250.scc`; the merged result depends on fragment order and is unknown until the first `.config`);
  - restated BSP values `CONFIG_ACPI`, `CONFIG_EFI`, `CONFIG_EFI_STUB`, `CONFIG_VIRTIO_PCI`, `CONFIG_VIRTIO_BLK`, `CONFIG_VIRTIO_NET`, `CONFIG_VIRTIO_CONSOLE`, `CONFIG_HW_RANDOM_VIRTIO` = y, so that `do_kernel_configcheck` flags any regression.
  - Correction to the first draft: NVMe and ENA are not absent from kernel-meta as a whole (other BSPs such as `bsp/intel-x86` and `bsp/nvidia-orin` set them); they are not set by `bsp/genericarm64/*.cfg` nor by any fragment `genericarm64.scc` includes, which is what matters.
- **`src/yocto/meta-egw/wic/egw-genericarm64.wks.in`.** poky's `genericarm64.wks.in` without its 44 MB swap partition (template line 7); root by `PARTUUID` (`--use-uuid`), so the disk boots whatever the device name (`/dev/vda`, `/dev/sda`, `/dev/nvme0n1`); root partition typed `B921B045-1DF0-41C3-AF44-4C6F280D3FAE` (`SD_GPT_ROOT_ARM64`, systemd 255.21 `sd-gpt.h` line 29) — the correct Discoverable-Partitions type, which nothing consumes at run time; no `console=` appended. Found through `WKS_SEARCH_PATH` (`image_types_wic.bbclass` line 45).
- **Shared with the first deliverable**: `egw-gateway-image.bb` and `egw-gateway-config.bb` — key-only operator `egw` (uid 1000) whose public key is read at `do_rootfs` from the host path in `EGW_AUTHORIZED_KEYS_FILE`. For an AMI this means the key is baked at build time: there is no cloud-init and no metadata-service fetch, and no key, password or credential is ever committed. `egw-gateway-image-dev` (debug-tweaks) is QEMU-only and must never be registered as an AMI.
- **AMI flow to try when an account exists** (borrowed from meta-aws; nothing executed): `aws s3 cp` the `.wic`; `aws ec2 import-snapshot --disk-container` with format RAW; `aws ec2 register-image --architecture arm64 --boot-mode uefi --virtualization-type hvm --ena-support --root-device-name /dev/sda1 …`; launch with a second EBS volume; watch the EC2 serial console at first boot; format the data volume; set `EGW_NTP_SERVERS` to 169.254.169.123 (vendor-documented Amazon Time Sync address). An alternative that avoids S3 and the `vmimport` role — writing the `.wic` with `dd` onto a blank EBS volume from a helper instance, then snapshot and `register-image` — is common practice and equally unverified here.

## 12. Addendum — corrections after the project review of 2026-09-18

A project review of the change set on 2026-09-18 requested five corrections and raised the MongoDB life cycle. Each claim was checked against the repository and the official sources before anything was changed; all five were confirmed. Nothing below has been run against Docker, a broker or a guest; every new script was parsed (`sh -n`, `dash -n`, `bash -n`) and exercised only with stubs or in a sandbox. 1. **Broker secrets (deployment blocker, confirmed).** Mosquitto 2 loads its configuration file and immediately drops to the unprivileged user; `password_file` and `keyfile` are opened after that (`src/mosquitto.c` v2.0.22: `config__parse_args`, `drop_privileges`, `mosquitto_security_init`, `listeners__start`). The comment in `generate-dev-tls.sh` that the broker reads the key as root was wrong. Correction: a new `src/deployment/scripts/prepare-broker-secrets.sh` gives `passwd` and `certs/server.key` to 1883:1883 with mode 0600, refuses any world-readable secret, and proves readability with a one-shot container running as that uid over the same read-only mounts as `compose.yaml`; `generate-dev-auth.sh`, `generate-dev-tls.sh` and `validate-config.sh` (new step 3b, `--check`) were adjusted; runbook Sections 5.3-5.5 and the deployment README were rewritten. These files belong to the deployment pull request, not to the first one.
2. **Confirmation deadline (confirmed).** Runbook Section 6.4 counted every `accepted` event and never read the controller clock. The harness rule is `CONFIRMATION_WINDOW_S = 60` (`src/egw_experiments/protocol.py` line 58) measured from the controller's `monotonic_ns` marker. Correction: a host-side helper `src/egw_experiments/itest_reconcile.py` imports the harness constants and accounting instead of re-implementing them, reports late confirmations separately, and labels a run without a marker as an eventual-delivery check only. Harness pull request.
3. **ACL test (confirmed).** The former test 9(d) started no publisher. Mosquitto's `acl_file` never refuses a SUBSCRIBE; it filters at delivery, and a denied PUBLISH is acknowledged normally under MQTT 3.1.1. Correction: `src/deployment/scripts/probe-acl.sh` runs an authorised and an unauthorised subscriber concurrently inside the broker container while tagged messages are published by both users on a topic outside the controller's subscription filter; the verdict is PASS, FAIL or INCONCLUSIVE, and INCONCLUSIVE is never reportable as a pass. Deployment pull request.
4. **Persistent counters (confirmed, and wider than reported).** Every test that compared the twin's cumulative `accepted_count` with one run's events now takes per-device snapshots before and after and compares the difference; `/metrics` comparisons are refused when the controller process restarted in between.

### 13.4 Observations that are not acceptance failures

1. `avahi-daemon` listens on UDP 5353: the `zeroconf` distro feature is still enabled in this profile. The guest sits behind slirp NAT, so nothing reaches it; on a physical gateway it would be exposure to review. Removing the feature would again change the kernel task signature (13.2, 10-A.5), not the kernel.
2. Runbook 2.5 read the QEMU version from `tmp/sysroots-components/`, where the binary cannot load `libfdt` on its own; the runbook now uses the image recipe's native sysroot.
3. The guest has no `systemd-analyze` and no rpm database (no package management in the image), so boot-time breakdown and an installed-package query must come from the build side (the manifest).
